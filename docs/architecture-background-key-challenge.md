# Gaming Hub 콘솔 연동 — 과제 배경과 핵심 아키텍처 난제

> 목적: Software Architect 인증 발표의 과제 배경 구간에서, 단순한 기능 요구사항이 아니라 왜 아키텍처 설계가 필요한 문제인지를 명확하게 설명하기 위한 발표용 정리

## 1. 발표에서 먼저 전달할 핵심

콘솔 연동의 어려움은 단순히 여러 시스템을 연결해야 한다는 데 있지 않다.

하나의 사용자 경험을 만들기 위해 클라우드의 사용자/콘텐츠 데이터, TV 화면, 네트워크 제어, HDMI 연결, 콘솔 장치의 실제 동작처럼 서로 독립적으로 동작하는 시스템들이 하나의 흐름처럼 일관되게 연결되어야 한다는 점이 핵심이다.

즉, 사용자는 TV에서 하나의 게임을 선택했을 뿐이지만 내부적으로는 여러 시스템과 통신 경로가 함께 맞물려야 하며, 이 중 하나라도 상태가 어긋나거나 제어가 실패하면 사용자가 기대한 결과와 실제 콘솔 동작이 달라질 수 있다.

## 2. 한 문장으로 말하면

> 콘솔 연동의 핵심 아키텍처 난제는, 서로 독립적인 클라우드·TV·네트워크·HDMI·콘솔 시스템의 상태와 제어를 하나의 일관된 사용자 경험으로 연결하는 것이다.

## 3. 발표용 설명 문장

다음처럼 설명할 수 있다.

> Gaming Hub에서 콘솔 콘텐츠를 TV에 제공하려면, 네트워크상의 사용자 및 콘텐츠 데이터가 먼저 TV 화면에 일관되게 표현되어야 합니다. 이후 사용자가 콘텐츠를 선택하면 해당 의도가 네트워크 제어와 HDMI 경로를 통해 실제 콘솔 장치의 동작까지 이어져야 합니다. 문제는 이 과정에 참여하는 시스템들이 서로 독립적으로 동작한다는 점입니다. 따라서 중간 단계의 상태 불일치, 응답 지연, 제어 실패가 발생하더라도 사용자가 하나의 자연스러운 흐름으로 느낄 수 있도록 상태와 제어를 일관되게 연결하는 것이 핵심 아키텍처 과제입니다.

## 4. “그래서 뭐가 어려운 건데요?”라는 질문에 대한 답

짧게는 다음과 같이 답할 수 있다.

> 독립된 시스템을 연계하는 과정에서 부분적으로 문제가 생길 수 있지만, 사용자에게는 하나의 흐름처럼 보여야 한다는 점이 어렵습니다.

조금 더 구체적으로는 다음과 같이 이어갈 수 있다.

> 예를 들어 TV에서는 사용자가 특정 게임을 선택했지만 콘솔 전원 상태, 현재 HDMI 소스, 파트너 서버의 상태, 딥링크 가능 여부가 서로 다를 수 있습니다. 네트워크 명령은 성공했지만 HDMI 전환이 실패할 수도 있고, 콘솔 전원은 켜졌지만 딥링크는 실패할 수도 있습니다. 따라서 일부 단계가 성공하고 일부는 실패하는 부분 실패와 상태 불일치를 관리하면서도, 사용자에게는 하나의 연속된 흐름으로 보이도록 설계해야 합니다.

## 5. Why → What → 어려움 → 설계에서 결정할 것

발표에서 길을 잃지 않기 위한 핵심 사고 틀은 다음 네 단계다.

### Why — 왜 이 요구사항이 필요한가

> 사용자는 TV에서 콘솔 콘텐츠를 쉽게 보고, 선택하면 실제 콘솔 게임 실행까지 자연스럽게 이어지는 경험을 원합니다.

### What — 그래서 무엇을 해야 하는가

> 파트너의 콘텐츠와 사용자 데이터를 TV에 보여주고, 사용자의 선택을 실제 콘솔 실행까지 연결해야 합니다.

### Difficulty — 그래서 뭐가 어려운가

> 독립된 시스템을 연계하는 과정에서 부분적으로 문제가 생길 수 있지만, 사용자에게는 하나의 흐름처럼 보여야 한다는 점이 어렵습니다.

핵심은 “여러 시스템이 있다”가 아니라, 각 시스템이 서로 다른 상태와 통신 방식을 가지고 있어 일부 단계만 성공하거나 실패할 수 있다는 점이다.

### Architecture Decision — 그래서 설계에서 무엇을 결정해야 하는가

> 시스템 간 정보를 어떤 경로로 전달할지와, 시스템의 상태와 제어를 어디에서 관리할지를 결정해야 합니다.

이 네 단계 이후에 실제 설계 대안과 선택 근거를 연결한다.

## 6. 요구사항과 아키텍처 문제를 구분해서 말하기

### 기능 요구사항

- 콘솔 게임 콘텐츠를 TV에 표시한다.
- 사용자가 게임을 선택할 수 있다.
- 콘솔 장치를 켠다.
- HDMI 소스를 전환한다.
- 네트워크 명령을 전달한다.
- 콘솔의 특정 게임 또는 상세 화면으로 딥링크한다.

위 항목은 “무엇을 해야 하는가”에 해당한다.

### 아키텍처 문제

- 각 시스템의 상태가 서로 다를 수 있다.
- 네트워크 명령 성공과 실제 장치 동작 성공이 동일하지 않을 수 있다.
- HDMI 전환, 콘솔 전원, 딥링크 실행이 서로 다른 시점에 완료될 수 있다.
- 부분 실패가 발생했을 때 사용자 경험을 어떻게 유지할지 결정해야 한다.
- 동일 사용자 의도가 여러 시스템을 거치면서도 일관되게 유지되어야 한다.

이 부분이 “왜 아키텍트의 설계가 필요한가”에 해당한다.

## 7. 과제 배경에서 추천하는 흐름

발표 초반에는 다음 순서가 자연스럽다.

1. **비즈니스 배경**  
   Gaming Hub에서 콘솔 콘텐츠를 TV 안으로 확장해, 콘솔 전원을 켜기 전에도 콘텐츠를 탐색하고 이후 실제 콘솔 실행까지 자연스럽게 이어지는 경험이 필요해졌다.

2. **사용자 관점의 목표**  
   사용자는 TV에서 콘텐츠를 보고 선택한 뒤, 복잡한 중간 절차를 의식하지 않고 실제 콘솔의 실행 위치까지 이동하기를 기대한다.

3. **기술적 현실**  
   하지만 실제 내부 구조는 클라우드, TV 애플리케이션, 파트너 서버, 네트워크 명령, HDMI/CEC, 콘솔 장치 등 여러 독립 시스템으로 나뉘어 있다.

4. **핵심 문제 정의**  
   따라서 이 시스템들의 상태와 제어를 하나의 사용자 흐름으로 일관되게 연결해야 한다.

5. **아키텍처 필요성**  
   이를 위해 상태 관리, 제어 순서, 실패 처리, 복구, 딥링크 연계까지 포함한 구조적 설계가 필요하다.

## 8. 발표에서 피하면 좋은 표현

다음 표현은 너무 일반적으로 들릴 수 있다.

- “연동할 시스템이 많아서 어렵습니다.”
- “HDMI와 네트워크를 같이 써야 해서 어렵습니다.”
- “여러 장치를 제어해야 합니다.”

가능하면 아래처럼 바꿔 말한다.

- “독립적인 시스템 간 상태 불일치를 제어해야 합니다.”
- “사용자 의도가 여러 제어 경로를 지나도 동일한 결과로 이어져야 합니다.”
- “부분 실패가 발생해도 전체 사용자 흐름의 일관성을 유지해야 합니다.”

## 9. 가장 짧은 발표 버전

> 사용자는 TV에서 콘솔 콘텐츠를 쉽게 보고, 선택하면 실제 콘솔 게임 실행까지 자연스럽게 이어지길 원합니다. 이를 위해 파트너 데이터와 사용자 선택을 TV에서 콘솔까지 연결해야 합니다. 하지만 독립된 시스템을 연계하는 과정에서 부분 실패와 상태 불일치가 발생할 수 있으므로, 사용자에게는 하나의 흐름처럼 보이도록 해야 합니다. 따라서 시스템 간 정보를 어떤 경로로 전달할지와 시스템의 상태와 제어를 어디에서 관리할지를 설계해야 합니다.
